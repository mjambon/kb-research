I found three potential issues with anchor relocation:

- **P0 — An anchor can silently move to an unrelated document.** Relocation ranks text matches without checking whether the destination was part of the move. If an anchor’s original text is deleted while an older, unrelated copy remains elsewhere, the anchor moves to that copy and becomes `Up_to_date`. The repository [already demonstrates this case](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/tests/Text_api_tests.ml:1090); the selection happens in [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:483).

- **P1 — Indexing order can leave a genuine move unresolved.** Relocation runs only when the anchor’s current document changes. If the old document is indexed before the destination, the attempt fails and records that revision; indexing the destination later does not retry it. A no-op reindex of the old document also leaves its revision unchanged. See [Text.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Text.ml:199) and [DB.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/DB.ml:852).

- **P1 — Repeated text can make an unchanged anchor unmatchable.** The index discards *every* occurrence of a repeated shingle within a document. Two identical functions in one file can therefore provide no indexed shingles for an anchor on either function; an unrelated edit can leave that anchor stale. See [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:150).
