I found two issues with anchor relocation:

- **P0 — An anchor can move to an unrelated copy even while its original text remains.** Candidates are ranked by shingle coverage and hit count, then by document ID; the original document gets no preference. If two documents contain the same anchored text, an edit elsewhere in the original document can move its anchor to the lower-ID copy. The new location is marked up to date, so the wrong evidence is easy to miss. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/base-libs/text/Anchor.ml:348)

- **P0 — Batch update order can leave a moved anchor permanently stale.** Each file is reindexed and its anchors relocated immediately. If the old file is processed before the destination has been indexed with the moved text, relocation fails. Indexing the destination later does not retry anchors still attached to the old file; a later update with no content change does not advance the old file’s revision to trigger another attempt. [Documents_update_cmd.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/cli/Documents_update_cmd.ml:438), [DB.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/base-libs/text/DB.ml:852)
