I found three potential issues with anchor relocation:

- **P0 — A moved anchor can remain stale because files are indexed in the wrong order.** Relocation runs only when the anchor’s current document is updated ([Text.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/base-libs/text/Text.ml:211), [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/base-libs/text/Anchor.ml:525)). If the old file is removed before the destination is indexed, the attempt fails. Indexing the destination later does not retry it, so the result depends on update order. The move test indexes the destination first.

- **P0 — An anchor can silently move to an unrelated document.** Candidate collection searches the global shingle index, and selection uses coverage without a source or original-document preference ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/base-libs/text/Anchor.ml:199), [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/base-libs/text/Anchor.ml:348)). Replacing anchored text can therefore make a claim point to an existing copy of that text, potentially in another source. A test already demonstrates this false positive ([Text_api_tests.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/base-libs/text/tests/Text_api_tests.ml:1096)).

- **P1 — Repeated text can prevent relocation even when the text survives.** Indexing drops *every* occurrence of a repeated shingle ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-orig/base-libs/text/Anchor.ml:150)). Copying an anchored block within its document can thus remove the shingles needed to find either occurrence, leaving the anchor stale.
