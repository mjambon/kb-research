I found three potential anchor relocation issues:

- **P0 — An unchanged anchor can move to an unrelated document.** Candidates are ranked by shingle coverage with no preference for the original document. Because coverage depends on the document’s shingle positions, an identical copy elsewhere can outrank the anchor’s intact text after an edit outside its range. The update then replaces the anchor’s document and contents, and marks it current. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:348), [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:495)

- **P0 — Cross-file moves depend on indexing order.** If the old file is indexed before the destination, relocation fails and records that revision as attempted. Indexing the destination later only checks anchors already attached to that destination, so the anchor remains outdated until the old file changes again. [Text.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Text.ml:199), [DB.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/DB.ml:852)

- **P1 — Minimum-length anchors can fail after a one-byte shift.** A 16-byte anchor has one query shingle, while document shingles are indexed every eight normalized bytes. Moving that exact text to an unindexed position yields no hit and leaves the anchor outdated. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:50), [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:152)
