I found three potential issues:

- **P0 — An anchor can silently move to unrelated evidence.** Relocation searches all indexed documents and ranks matches without preferring the original document or source ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:348)). If the anchored text is replaced while an unrelated file contains the same boilerplate, the anchor becomes up to date on that file. An existing test demonstrates this false positive ([Text_api_tests.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/tests/Text_api_tests.ml:1094)). That can make a claim appear supported by the wrong code.

- **P1 — Failed cross-file moves can remain stale indefinitely.** A failed attempt advances `doc_revision_attempt`, and relocation is retried only when the anchor’s *current document* gets a newer revision ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:491), [Text.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Text.ml:211)). If its text appears in another file after the failed attempt, indexing that destination does not retry the anchor.

- **P1 — Short anchors can fail to relocate after an unrelated edit.** A 16-byte anchor has one query shingle, but document shingles are indexed only every eight normalized bytes ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:152)). If that anchor starts between indexed offsets, the matcher has no hit even when its text remains unchanged.
