I found three potential issues with anchor relocation:

- **P0 — An anchor can move away from text that still exists.** Candidates are ranked by shingle coverage, then hit count, then document ID, with no preference for the original document ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments/base-libs/text/Anchor.ml:348)). If an earlier indexed document contains the same excerpt and an unrelated edit changes the original document’s revision, the anchor can move to the earlier document. That changes what a claim cites even though its original text remains intact.

- **P1 — A failed move may never be retried.** A failed search records the current revision as attempted ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments/base-libs/text/Anchor.ml:490)), and relocation only selects anchors whose attempted revision is older than their document’s revision ([DB.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments/base-libs/text/DB.ml:852)). If the source is processed before the destination receives the moved text, indexing that destination later does not retry the anchor. It stays outdated until the source changes again.

- **P1 — Repeated text can prevent an exact relocation.** The index discards every occurrence of a shingle that repeats within a document ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments/base-libs/text/Anchor.ml:152)). An anchor in duplicated code can therefore have no searchable shingles, leaving it outdated after an unrelated edit even when its exact text remains.
