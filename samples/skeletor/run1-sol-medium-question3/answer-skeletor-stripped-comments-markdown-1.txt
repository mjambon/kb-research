I found three potential issues with anchor relocation:

- **P0 — An anchor can silently move to unrelated text.** The matcher searches every indexed document and selects the highest coverage candidate without checking whether the text actually moved there ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/Anchor.ml:348)). An existing test demonstrates an anchor moving to an unrelated file that contains the same boilerplate ([Text_api_tests.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/tests/Text_api_tests.ml:1096)). The anchor then appears up to date while pointing at the wrong evidence.

- **P1 — A failed relocation is not retried when its destination is indexed later.** A failed attempt records the source document’s current revision ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/Anchor.ml:491)). Future attempts select only anchors whose recorded attempt predates a revision change in that same document ([DB.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/DB.ml:852)). If the destination is added afterward, the anchor stays outdated until the source changes again.

- **P1 — Short anchors can become outdated after a simple shift.** Documents store 16 byte shingles only at eight byte intervals ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/Anchor.ml:167)), while 16 byte anchors are accepted ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/Anchor.ml:554)). A 16 byte anchor shifted to a position between indexed intervals has no matching shingle, even when its text is intact.
