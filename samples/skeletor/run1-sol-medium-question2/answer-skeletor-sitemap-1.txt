During relocation, each file with a qualifying match becomes a candidate. The code chooses the candidate with the most matched shingle coverage, then the most hits, then the **lowest document ID**. It gives the anchor’s original file no preference and automatically updates the anchor to the winner. So even with exact copies in several files, the destination can depend on indexing details or document creation order. See [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:348) and the [selection log](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:419).

That is deterministic, but I would not consider it desirable for ambiguous matches. An exact copy does not establish that the text moved; the tests document a case where an anchor relocates to an unrelated copy in another file ([Text_api_tests.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/tests/Text_api_tests.ml:1097)). Prefer the original file when its match survives, and leave genuinely ambiguous cross-file matches for review.
