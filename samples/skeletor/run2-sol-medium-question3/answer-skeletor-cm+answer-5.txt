I found four potential issues in anchor relocation:

- **P0 — An unrelated edit can move an intact anchor to another file.** Candidates are ranked by text coverage and document ID, with no preference for the anchor’s current document. If an earlier indexed file contains the same text, relocation can change the anchor’s document even though its original span is still intact. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:355)
- **P0 — An acknowledged anchor can become stale without appearing for review.** Relocation keeps `acknowledged_revision` when it changes documents. If the destination has a lower revision, a later failed relocation can leave `needs_review` false until that document’s revision passes the old acknowledgment number. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:512)
- **P0 — Relocation can cross registered sources.** Hit collection searches the global shingle index without restricting candidates to the anchor’s source. Removing text from one source can therefore attach its anchor to an unrelated identical snippet in another. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:206)
- **P1 — Repeated text can make an intact anchor stale.** Indexing drops every occurrence of a shingle that repeats within a document. A short anchor present twice may have no usable hits after an unrelated edit, so relocation leaves it outdated. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:159)
