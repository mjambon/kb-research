I found five potential issues in anchor relocation, based on code inspection:

- **P0 — An intact anchor can jump to a duplicate in another file.** Candidate ranking breaks ties by document ID, with no preference for the current document. An unrelated edit can therefore move an anchor away from text that is still intact. [Anchor.ml:355](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:355)
- **P0 — Relocation can cross source boundaries.** Shingle lookup searches all indexed documents without checking the anchor’s source. Deleting text in one repository can attach its anchor to identical, unrelated text in another. [Anchor.ml:206](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:206)
- **P0 — A failed relocation can be hidden from review.** Relocation retains `acknowledged_revision` when moving to a document with a lower revision. If relocation then fails on that document’s next update, `needs_review` can remain false until its revision exceeds the old acknowledgment. [Anchor.ml:512](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:512), [Anchor.ml:116](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:116)
- **P1 — Repeated text can become outdated while intact.** Indexing drops every occurrence of a repeated shingle. A short anchor appearing twice can have no relocation hits after an unrelated edit. [Anchor.ml:159](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:159)
- **P1 — Some valid 16-byte anchors cannot relocate.** Document shingles start only at offsets divisible by eight, while a 16-byte anchor has just one query shingle. If its intact text starts at another offset, relocation finds no hit. [Anchor.ml:174](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:174), [Anchor.ml:209](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:209)
