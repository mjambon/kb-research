I found three potential issues with anchor relocation:

- **P0 — A move can be missed permanently when files are indexed in the wrong order.** Relocation runs when the anchor’s original document is updated, and it searches only documents already indexed at that moment. If the old file is processed before the destination, the attempt fails. Indexing the destination does not retry that anchor, and an unchanged reindex of the old file does not retry it either. The anchor stays outdated until the old file changes again. See [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:525) and [DB.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/DB.ml:852).

- **P0 — An unrelated copy can silently become the anchor’s new location.** Candidate selection searches across documents and gives the original document no preference. If the anchored text is replaced while another file contains the same boilerplate, relocation marks the unrelated copy *up to date*. A regression test documents this false positive. See [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:348) and [Text_api_tests.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/tests/Text_api_tests.ml:1096).

- **P1 — Repeated text loses all matching shingles.** The index discards every occurrence of a repeated shingle, including the first. Anchors made of repeated text can therefore fail to relocate after a simple shift, even when the text remains present. See [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:150).
