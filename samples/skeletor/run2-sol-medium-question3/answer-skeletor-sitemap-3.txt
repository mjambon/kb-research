I found three anchor relocation issues:

- **P0 — An unrelated copy can silently become the anchor’s destination.** When the original text disappears, relocation searches every indexed document and selects the strongest text match without evidence that the text moved there. An existing test demonstrates an anchor moving onto unrelated boilerplate in another file. This can make a claim point to the wrong source while appearing up to date. See [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Anchor.ml:348) and the [documented test](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/tests/Text_api_tests.ml:1097).

- **P1 — Cross-file moves depend on indexing order.** If the source is indexed after its text is removed but before the destination is indexed, the relocation attempt fails. Indexing the destination later retries only anchors attached to that destination, leaving the source anchor outdated until the source changes again. See [Text.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/Text.ml:199) and [DB.ml](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/DB.ml:852).

- **P1 — Small, evenly spaced edits can defeat relocation.** Changes every eight bytes can invalidate every indexed 16-byte shingle even when most anchor bytes survive. With no hits, alignment never runs and the anchor becomes outdated. This is reproduced in the [borderline tests](/workspace/kb-research/samples/skeletor/skeletor-sitemap/src/skeletor/base-libs/text/tests/Text_api_tests.ml:1060).
