I found three potential issues:

- **P0 — An unchanged anchor can move to an unrelated copy.** Relocation ranks candidates by shingle coverage, then hit count, then document ID, with no preference for the anchor’s current document ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/Anchor.ml:348)). If an earlier-indexed file contains the same passage, updating the original file can silently move its anchor to that copy even when the passage remains intact in the original. That changes what document the anchor cites.

- **P1 — A failed relocation is not retried when the destination arrives later.** Failed attempts record the current revision ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/Anchor.ml:490)), while updates only retry anchors belonging to the document being updated ([DB.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/DB.ml:852)). If the old file is removed before its replacement is indexed, adding the replacement leaves the anchor outdated until the old document changes again.

- **P1 — A one-byte insertion can orphan a minimum-length anchor.** Document shingles are indexed only at eight-byte intervals ([Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-stripped-comments-markdown/base-libs/text/Anchor.ml:167)). A 16-byte anchor has only one possible shingle; inserting one byte before it shifts that shingle off the indexed positions, so relocation finds no candidate despite an exact match.
