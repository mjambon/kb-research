I found four potential issues with anchor relocation:

- **P0 — An unrelated edit can move an intact anchor to another file.** Candidate ranking has no preference for the current document. When two files contain the same anchored text, a tie can select the file with the lower document ID even though the original span is still present. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:355)
- **P0 — Relocation can cross source boundaries.** The shingle lookup searches all indexed documents without checking the anchor’s source. Text removed from one repository can cause its anchor to attach to an identical snippet in another source. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:206)
- **P0 — Relocation can suppress a later review warning.** Moving an acknowledged anchor to a document with a lower revision preserves its old `acknowledged_revision`. If the next relocation fails, `needs_review` can remain false until the new document’s revision exceeds that old value. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:512)
- **P1 — Repeated text can leave an intact anchor stale.** Indexing discards every occurrence of a repeated shingle. A short anchor whose text occurs twice may therefore have no searchable hits after an unrelated edit. [Anchor.ml](/workspace/kb-research/samples/skeletor/skeletor-cm+answer/base-libs/text/Anchor.ml:159)
